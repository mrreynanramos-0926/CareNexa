# CareNexa Database Specification

| Field | Value |
| --- | --- |
| Version | 0.1 Draft |
| Status | Pending approval |
| Date | 2026-10-03 |
| Engine (MVP) | SQLite via Prisma |
| Engine (later) | PostgreSQL via the same Prisma models |

Money columns are integers in centavos (SRS Assumption A-01). Timestamps are UTC `DateTime`. The names below are logical. Prisma models use PascalCase singular names and map to these snake_case tables.

## 1. ERD description

```
roles 1───* users *───1 (created_by) marketing_campaigns
                │
                * audit_logs
                *
                activities *───1 customers

customers 1───* customer_segment_memberships *───1 customer_segments
customers 1───1 customer_lifetime_value
customers 1───* orders 1───* order_items *───1 products_services
customers 1───* marketing_messages *───0..1 marketing_campaigns

products_services 1───0..1 inventory
products_services 1───* inventory_movements     (proposed)
products_services 1───* inventory_alerts
orders 1───* anomaly_alerts

customer_segments 1───* marketing_campaigns
users 1───* marketing_campaigns (created_by)

trigger_rules are standalone configuration
system_settings are standalone configuration (proposed)
```

A customer does not need a segment to exist. A service does not need an inventory row. A marketing message may be created by a campaign or by a trigger rule.

## 2. Conventions

| Topic | Rule |
| --- | --- |
| Primary keys | `id` string, cuid or uuid, generated by the application or Prisma |
| Foreign keys | Required when the relationship is mandatory; `ON DELETE RESTRICT` for business history |
| Timestamps | `created_at` and `updated_at` on mutable business rows |
| Audit fields | `created_by` where the brief already names it; other actors are captured in `audit_logs` |
| Status fields | String enums validated in application code and, where Prisma supports it on both engines, native enums or checked strings |
| Soft status | Customers and users are deactivated by `status`, not deleted, when history exists |
| JSON | `criteria` and audit value payloads are JSON text. Keep the shape small and documented. |

Prisma on SQLite does not enforce all check constraints the way PostgreSQL does. The service layer enforces enums. PostgreSQL migrations may add `CHECK` constraints later without changing services.

### 3.4 customer_segments

| Column | Type | Notes |

| id | string PK | |

| created_at | datetime | |

Criteria shape:

```json
{
  "match": "all",
  "rules": [
    { "field": "total_spent_centavos", "op": "gte", "value": 5000000 },
    { "field": "visit_count_in_days", "op": "gte", "value": 12, "windowDays": 365 }
  ]
}
```

Allowed fields: `total_spent_centavos`, `visit_count`, `visit_count_in_days`, `days_since_last_visit`, `days_since_first_visit`, `days_since_created`.

Allowed operators: `gte`, `lte`, `eq`.

`match` is `all` or `any`. VIP uses `any` for spend or visits (BR-003). Other seeded segments use `all`.

Unique open alert on `(transaction_id, anomaly_type)` for order-scoped types. `sales_spike` uses a synthetic daily order only if a real anchor order exists: the largest order that day is the linked transaction, and `dedupe` is the business date stored in `description` plus a unique key. **Pending column:** `dedupe_key` on anomaly alerts so spikes are not duplicated. ## 6. Derived metrics

Not stored on the customer row:

- days since last visit: from `customer_lifetime_value.last_visit_date` to today in Asia/Manila
- new customers: `customers.created_at` inside the selected range
- active customers: status `active` and not in the Inactive segment after the latest segmentation run

Segmentation must run after value recalculation so criteria see fresh totals.

## 7. Migration strategy

1. `prisma migrate dev` creates SQL migrations checked into git.
2. Migration 001 creates the approved tables only.
3. Pending columns from C-04, C-05, and C-06 ship as a later migration after approval, not as silent edits to production data.
4. Seeds are not migrations. `prisma db seed` loads roles, settings, demo users, and fictional clinic data.
5. Moving to PostgreSQL: change `provider` and `DATABASE_URL`, run the migration history against an empty PostgreSQL database, and reseed. Integer money columns do not need conversion.
6. SQLite file `dev.db` is gitignored.

## 8. Seed outline

Fictional Manila clinic data:

- Roles: Admin, Manager, Staff
- Users: one of each, passwords from the environment
- Settings: Assumption A-02
- 6 segments with the criteria shape
- 12 catalog rows mixing facial services and retail products; only products track inventory
- 30 or more customers with birthdays spread across the year, including at least one birthday on the seed “today” only if tests freeze time; otherwise tests create that customer
- 50 or more completed orders across the prior 90 days, a few voided orders once void fields exist, PHP prices in a clinic-plausible range
- Memberships produced by running the segmentation service, not hand-waved in a way that contradicts criteria
- At least two campaigns and their message logs
- Inventory quantities that include one low-stock and one out-of-stock product
- Anomaly rows that match orders the rules would actually flag

Sample names: Maria Santos, Juan Dela Cruz, Ana Reyes, plus other clearly fictional names. No real phone numbers; use the `09xxxxxxxxx` range reserved in seed as obviously fake `09000000xxx` sequences.
